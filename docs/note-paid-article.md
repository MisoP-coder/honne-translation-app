# note 有料記事の下書き(スマホ開発記)

## この記事の設計

**有料記事は「日記」では売れません。** 読んだ人が同じ穴に落ちなくなる、という価値で値段をつけます。

そのため、無料部分と有料部分を次のように分けています。

| | 内容 | 狙い |
| --- | --- | --- |
| **無料部分** | 何を作ったか、道具と費用の内訳、かかった日数、AI に書かせたという正直な告白 | 「本当にスマホだけでできたのか」を疑う人に、具体的な数字で信用してもらう |
| **有料部分** | 実際に詰まった10箇所と、その抜け方 | ここが商品。1箇所でも同じ罠を避けられれば、数百円は回収できる |

無料部分の最後に「ここから先は、実際に詰まった10箇所です」と書いて期待を作り、そこに**有料ラインを設定**します。

## 価格の案

**500円**を推奨します。

- 100〜300円: 気軽に買われますが、内容が薄いと思われます
- **500円: 有料部分が約5,000字の実用情報なので、これで妥当。個人開発系の実用記事の相場です**
- 1,000円以上: 実績のあるアカウントでないと、購入ボタンの前で手が止まります

## 確認してほしいこと

事実関係は実際に起きたことをそのまま書いていますが、**気持ちの描写は私の推測**です。次の箇所はご自身の言葉に置き換えてください。

| 記事の中の記述 | 確認 |
| --- | --- |
| 「正直、心が折れかけた」(404 のくだり) | 実感に近い表現に |
| 「画面の小ささが最大の敵だった」 | 実際にいちばん辛かった点に |
| かかった日数「10日ほど」 | 実際の日数に |
| 「通勤時間と寝る前の1〜2時間」 | 実際に触っていた時間帯に |
| 「設定を疑って1時間使いました」(404 のくだり) | 実際にかかった時間に |

## 有料部分(ここから先を有料に)

```
■ 1. デプロイ成功。なのに404

Vercelで「Congratulations!」と出たので、URLを開いたら404でした。
設定を疑って1時間使いましたが、原因は別のところにありました。

GitHubのmainブランチに、README.mdしか入っていなかったのです。

コードはプルリクエストの中にあって、マージしていませんでした。
Vercelはmainブランチを見て公開するので、そこに何も無ければ404になります。

抜け方: GitHubでプルリクエストを開き、緑のMergeボタンを押す。
それだけでした。

いま思えば当たり前ですが、当時は「デプロイが成功した」という表示を信じて、
公開まで終わったと思い込んでいました。正直、心が折れかけました。

教訓: Vercelの「成功」は「mainブランチの内容を配った」という意味しかない。
mainに何が入っているかは、別途GitHubで確認する必要があります。


■ 2. No Output Directory named "public" found

次に出たのがこれです。ビルドが途中で止まりました。

原因は、VercelがこのアプリをNext.jsだと認識していなかったことです。
プロジェクトを取り込んだ時点でmainにpackage.jsonが無かったため
(1番の状態です)、種類の判定が別のものに固定されてしまっていました。

抜け方: リポジトリのルートに vercel.json というファイルを作り、
中身をこう書きます。

{"framework": "nextjs"}

ダッシュボードの設定画面から直すこともできますが、スマホだと
その設定項目を探すのがとにかく大変でした。ファイルを1つ置くほうが速いです。

教訓: スマホでの開発では、「設定画面をいじる」より
「設定ファイルを置く」ほうが圧倒的に楽です。
ダッシュボードはスマホ向けに作られていません。


■ 3. 新規登録を押したら Invalid path specified in request URL

アプリの画面は出たのに、アカウントが作れませんでした。

原因は、Supabaseの接続先URLの貼り間違いです。
Supabaseの画面から、こういうURLをコピーして貼っていました。

https://xxxxx.supabase.co/rest/v1/

正しかったのは、これです。

https://xxxxx.supabase.co

/rest/v1/ の部分は、APIの入口を示す別のURLでした。
Supabaseの画面には似たURLが複数並んでいて、どれが「Project URL」なのか
一目で分かりません。

抜け方: 末尾に余計なパスが付いていないか確認する。
ドメインだけにする。

教訓: コピーできたURLが、目的のURLとは限りません。
エラーに path や URL という単語が出たら、まずここを疑うと速いです。


■ 4. 環境変数が保存できない

APIキーなどをVercelに登録しようとして、こう出ました。

Environment variables with a public framework prefix cannot use visibility: secret

これには2段構えの罠があります。

まず、NEXT_PUBLIC_ で始まる変数は Secret にできません。
これらはブラウザに埋め込まれる公開値なので、秘密にする意味がないからです。
Type は Config を選びます。

さらに厄介なのが、一度 Secret で保存してしまった変数は、
あとから Config に変更できないことです。

抜け方: 該当の変数を削除して、Config で作り直す。

逆に、本物の秘密(私の場合はAnthropicのAPIキー)は Secret のままにします。
こちらはブラウザに出てはいけない値なので、区別が必要です。

教訓: 変数の名前の頭に NEXT_PUBLIC_ が付いているかどうかで、
扱いが変わります。付いていたら公開値、付いていなければ秘密です。


■ 5. 直したのに、いつまでも反映されない

これがいちばん長く苦しみました。
設定を直して、コードも直して、それでも画面が変わらない。

原因は2つありました。

ひとつ目。Vercelには2種類のURLがあります。

・本番のURL(短い。プロジェクト名だけ)
・デプロイごとのURL(長い。途中にランダムな文字列が入る)

私はデプロイごとのURLをブックマークしていました。
このURLは「そのときのデプロイ」に固定されていて、永久に変わりません。
新しく直しても、古い画面をずっと見続けることになります。

ふたつ目。環境変数は、保存しただけでは反映されません。
値はビルドのときにアプリへ埋め込まれるので、保存後に再デプロイが必要です。

抜け方:
・Vercelの Domains に出ている短いURLを開く。ブックマークもそちらにする
・環境変数を直したら、Deployments → 最新の「…」→ Redeploy

教訓: 「直したのに変わらない」と思ったとき、
自分が見ている画面が古いのか、直した内容が届いていないのか、
まずどちらなのかを切り分けます。ここを飛ばすと無限に迷います。


■ 6. ボタンが画面からはみ出す

「無料で始める」ボタンが、右端から少しはみ出していました。

原因は、幅の計算方法の違いです。
リンクとして作ったボタンは、標準では「内側の余白を幅に含めない」
という計算をします。幅100%を指定した上に左右16pxずつ余白を足すと、
画面より32px大きくなります。

抜け方: CSSに1行足すだけです。

* { box-sizing: border-box; }

これで、余白を含めた全体が指定の幅になります。

教訓: スマホでの見た目の崩れは、たいていこの幅計算が原因です。
1箇所を直すより、この1行を最初から入れておくと事故が減ります。


■ 7. メールの文面が、どうしても編集できない

アプリが送るパスワード再設定メールが英語のままでした。
差出人も「Supabase Auth」で、どのアプリからのメールか分かりません。

Supabaseの管理画面に文面の設定はあります。
でも、入力欄が触れませんでした。

原因: 無料プランで標準のメール送信を使っているあいだは、
テンプレートの編集がロックされています。
無料枠のメール送信が、フィッシングメールの配信に悪用された件を受けた制限です。

抜け方は2つあります。

・外部のメール送信サービス(Resendなど)を登録する。ロックが外れます
・アプリ側で「英語のメールが届きます」と案内してしまう

私は当面、後者にしました。
送信直後の画面に「差出人はSupabase Auth、件名はReset Your Passwordの
英語のメールです」と出すようにしたら、実用上は困らなくなりました。

教訓: 直せない制限にぶつかったとき、
「その制限を回避する」以外に「制限があることを伝えてしまう」
という手があります。後者は5分で終わります。


■ 8. 「特に問題なかったよ」がいちばん危ない

知人に何人か試してもらいました。返ってきたのは
「特に問題なさそう」でした。

安心しかけたのですが、念のため利用状況を数える仕組みを入れて、
データを見てみました。

相談まで到達していたのは、2人だけでした。

頼まれて触った人は、詰まっても「自分の使い方が悪いのかな」と思って
黙って離れます。悪気はまったくありません。そういうものです。

抜け方: 感想を聞くのをやめて、行動を数えます。

・何人が登録したか
・そのうち何人が最後まで進んだか
・2回以上使った人は何人か

段階ごとに人数を並べると、どこで人が落ちているかが一目で分かります。
私の場合、登録した3人のうち2人は相談まで進んでいたので、
入口ではなく「そもそも人数が足りていない」ことが分かりました。

教訓: 「問題なかった」は、問題が無い証拠ではありません。
数字だけが本当のことを言います。


■ 9. 目玉の機能が、一度も動いていなかった

このアプリの売りは「使うほど、その上司に合った予測になる」ことです。
結果を記録すると、それをもとに予測が変わります。

データを見たら、その機能が発動した回数はゼロでした。

バグかと思って調べましたが、コードは正しく動いていました。
原因は設計のほうにありました。

記録は、相談した「あと」に増えます。だから、

1回目の相談 → 記録0件 → 一般論
記録が1件に
2回目の相談 → 記録1件 → 一般論
記録が2件に
3回目の相談 → 記録2件 → 一般論
記録が3件に
4回目の相談 → ようやく発動

切り替えに3件必要な設計にしていたので、
同じ上司に4回相談しないと、売りの機能に届かなかったのです。

作った本人は到達していました。他の誰も到達していませんでした。

抜け方: 必要な件数を3件から2件に下げました。3回目で発動します。

教訓: 「何回使えばこの機能に届くか」を数えてみてください。
作った本人は何十回も触るので、絶対に気づけません。
数えれば一瞬で分かります。


■ 10. お名前.comのCNAME設定

最後の関門でした。取得したドメインをアプリに繋ぐ作業です。

Vercelが表示した設定値を、お名前.comに登録します。
ここで2つ間違えました。

ひとつ目。ホスト名の欄です。
使いたいURLが honne.misop-craft.com なら、
ホスト名に入れるのは honne だけです。

全部入れてしまうと、honne.misop-craft.com.misop-craft.com という
おかしなものができあがります。

ふたつ目。Vercelは設定値を、末尾にドットを付けて表示します。

xxxxx.vercel-dns-017.com.

この最後のドットは「完全なドメイン名」を示すDNSの記法です。
お名前.comの入力欄はドット無しが前提なので、付けると弾かれます。

それから、設定しても繋がらない場合の確認箇所がもう1つあります。
お名前.comの「ネームサーバーの設定」で、
01.dnsv.jp 〜 04.dnsv.jp が入っているかを見てください。
ここが別のものだと、いくらDNSレコードを設定しても無視されます。

反映には数十分から数時間かかります。最大24時間です。
待つしかない時間があることは、最初から知っておいたほうが精神的に楽です。


■ スマホだけで進めるために効いたこと

画面の小ささが最大の敵でした。
その中で、これは効いたという工夫を挙げます。

1. 設定はダッシュボードよりファイルで
   さっきのvercel.jsonのように、設定ファイルで済むならそちらにします。
   スマホのダッシュボードは、項目を探すだけで疲れます。

2. 管理画面はURLの直打ちで開く
   VercelもSupabaseも、URLの末尾にパスを足せば目的の画面に直接飛べます。
   Vercelなら /settings/domains、Supabaseなら /auth/url-configuration など。
   メニューを辿るより何倍も速いです。

3. エラーは全文をスクショで送る
   要約して伝えると、原因の特定が遅れます。
   長くても全部見せたほうが、一発で分かることが多いです。

4. 手順書を自分用に作っておく
   同じ設定を2回目にやるとき、前回どうしたか絶対に忘れています。
   詰まって解決したら、その場で手順を書き残すようにしました。


■ 次に作るなら、順番を変えます

いま振り返って、いちばん無駄だったのは順番の間違いです。

私はこうやりました。
アプリを作る → 公開する → 計測を入れる → 人に見せる

次はこうします。
計測を先に入れる → アプリを作る → 人に見せる → 数字を見てから直す

計測を後回しにしたせいで、8番と9番の問題に気づくのが遅れました。
先に入れておけば、最初の1人が使った時点で分かったはずです。

数える仕組みは、あとから入れると過去のデータが取れません。
これだけは最初に入れることをおすすめします。


■ まとめ

スマホだけでWebアプリは公開できます。これは確かです。

ただ、AIがコードを書いてくれる時代になっても、
詰まる場所が消えたわけではありませんでした。
場所が「コードの中」から「コードの外」に移っただけです。

デプロイ、環境変数、ドメイン、外部サービスの制限、そして計測。
ここはまだ人間が判断する領域として残っています。

逆に言えば、ここを1回通ったことが、今回いちばんの収穫でした。
2つ目を作るときは、10日ではなく数日で公開まで行けると思います。

同じところで止まっている人に、この記録が届いたらうれしいです。
```

## 公開したあとに

1. **無料記事(なぜ作ったか)から、この記事へリンクを張る** — 逆は張りません。無料記事で共感した人が「作り方も知りたい」と思ったときに導線があるのが自然です
2. **X では無料記事を先に出す** — 有料記事を単体で投げると宣伝に見えます
3. **売れた数を記事に追記する** — 「○部売れました」という追記は、後から来た読者の判断材料になります

## 書き足せるとさらに良くなる部分

- **各項目のエラー画面のスクショ** — 同じエラーで検索してきた人が「これだ」と分かります。有料記事の価値がかなり上がります
- **実際の作業時間の内訳** — 「10日のうち、詰まっていた時間が6日」のような数字は生々しくて読まれます
- **かかったAPI費用の実額** — 公開後の数字が出たら追記すると、これから始める人の判断材料になります
